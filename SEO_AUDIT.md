# PopSpot SEO Audit — pop-spot.vercel.app

Full-site audit via `/seo audit`, 10 parallel specialist passes (technical,
content, schema, sitemap, performance, visual/mobile, GEO/AI-search,
search-experience, local, backlinks), all live-tested against production.

Expected for a site that launched days ago — the score isn't a verdict on
the work, it's a map of exactly where the leverage is. And the map is
unusually clear here: **almost every finding below traces back to one root
cause**, not seven unrelated problems.

## The one root cause behind most findings

This is a client-rendered SPA with no server-side rendering framework. A
Vercel Edge Middleware (`middleware.js`) plugs the biggest gap by serving a
real static snapshot to known crawlers — **but only for `/space/:slug`
listing pages.** Every other route (`/`, `/search`, `/faq`, and every
private/authenticated page) serves the identical generic empty shell to
everyone, crawlers included, until client JS executes.

Verified live (fetched with real Googlebot/GPTBot/etc. User-Agents):

- `/space/villa-pool-herzliya` → Googlebot, Facebook, Twitter all get the
  real title/description/price/JSON-LD snapshot. **GPTBot, ClaudeBot,
  PerplexityBot, OAI-SearchBot, CCBot, anthropic-ai, Bytespider all get the
  same empty `<div id="root"></div>` a plain browser gets before JS runs.**
  The bot-detection regex (`BOT_UA` in `middleware.js`) simply never
  included the AI-assistant crawlers.
- `/search?city=X&category=Y` — the exact pages carrying the templated
  city×category landing copy built for this — gets **no snapshot at all**,
  not even for Googlebot. Same for `/`  and `/faq`.
- `/login`, `/profile`, `/favorites`, `/bookings`, `/admin`, `/host/*` —
  all return HTTP 200, byte-identical to the homepage (same ETag), with
  **no server-side noindex signal whatsoever** — no `X-Robots-Tag` header,
  no `<meta>` tag in the raw HTML, no `robots.txt` Disallow rule. The only
  thing preventing indexing is a client-side `document.title`/meta
  mutation that runs after React mounts — a race, not a guarantee.
- Any nonexistent path (`/this-page-does-not-exist`) returns HTTP 200 with
  the same shell — a soft-404, which can waste crawl budget and confuse
  indexing signals.
- `sitemap.xml` lists only 11 URLs (home, search, faq, 8 listings) — **none
  of the 110 possible city×category combinations** the SEO content work
  actually targets are in it, because they're generated by client-side
  routing with no corresponding static/snapshot page.
- `llms.txt` returns HTTP 200 with the SPA shell instead of a real file or
  a clean 404 — a false-positive that could confuse simple AI-tool
  existence checks.

## Prioritized action plan

**Critical**
1. Extend the `middleware.js` bot-snapshot pattern from `/space/:slug` to
   `/search` (using the `getSearchLandingCopy` content that already
   exists in `seoContent.js` but currently only reaches the DOM after JS
   runs) and to `/` and `/faq`.
2. Add the missing AI crawler UAs to `BOT_UA`: `GPTBot`, `OAI-SearchBot`,
   `ChatGPT-User`, `ClaudeBot`, `Claude-Web`, `anthropic-ai`,
   `PerplexityBot`, `Perplexity-User` (optionally `CCBot`). Pure allow-list
   expansion, no security implication — same static read-only content
   already served to Googlebot.
3. Add a server-side `noindex` signal for private routes — either an
   `X-Robots-Tag: noindex` header set in middleware for those path
   prefixes, or (better long-term) gate them behind real auth so
   unauthenticated requests 302 to `/login` instead of returning 200.
4. Add explicit `Disallow` rules to `robots.txt` for `/login`, `/register`,
   `/favorites`, `/bookings`, `/profile`, `/host/`, `/admin` as a
   belt-and-suspenders measure alongside #3.
5. Generate sitemap entries for city×category combinations once #1 makes
   them real, indexable pages (110 permutations; skip any with a
   currently-empty result set to avoid thin-content bloat).

**High**
6. Add `Vary: User-Agent` to the middleware's snapshot response headers —
   without it, an intermediary cache could theoretically serve a bot
   snapshot to a real visitor or vice versa. Low risk today, becomes more
   likely as the bot UA list grows.
7. Add real crawlable `<Link>`/`<a href>` internal links to city×category
   combinations (currently the city picker is a `<select>` + `onClick
   navigate()` — zero crawlable hrefs for any city, anywhere in the app).
8. Return a real 404 (or at least a noindex) for unmatched paths instead
   of the current soft-404.
9. Expand per-listing descriptions — currently ~15-20 words in the bot
   snapshot, well under a citable/useful length. Add amenities and rules
   text into the snapshot body, not just the interactive SPA.
10. Turn `/faq` into real question-phrased H2/H3 blocks with
    self-contained answers once it's server-rendered (better for both
    classic snippets and AI-answer citability) — do NOT add `FAQPage`
    JSON-LD for it though: Google retired FAQ rich results for all sites
    in 2026, so schema effort there wouldn't buy a SERP feature.

**Medium**
11. Publish a real `llms.txt` (or return a clean 404) instead of the
    current false-200 SPA-shell response.
12. Add `Organization`/`WebSite` JSON-LD to the homepage (currently zero
    schema at the brand level) — helps AI-overview/Knowledge-Panel
    entity recognition.
13. Self-host or `preload` the Google Fonts (Archivo, Source Sans 3)
    instead of the current render-blocking `<link>` — a real,
    unmeasured-but-known Core Web Vitals cost.
14. Consider whether a marketplace-wide Google Business Profile is worth
    pursuing at all — a specialist pass concluded it's a defensible but
    secondary lever (category mismatch risk for non-rental categories,
    can't represent 11 cities under one profile) and that the primary
    local-SEO investment should go into #1/#5 instead.

**Low**
15. Make the `<lastmod>` values in the sitemap meaningful — all 8 listings
    currently share the exact same millisecond timestamp (reads as a bulk
    seed-data date, not real update tracking); Google may learn to
    distrust the signal domain-wide if this persists.
16. Add `priority`/`changefreq` — actually correctly *omitted* today
    (Google ignores both), no action needed, noted for completeness.

## What's already solid — no action needed

- `sitemap.xml` itself is well-formed, correctly declared in `robots.txt`,
  correctly excludes non-indexable URLs, served with the right MIME type.
- The `Product`/`Offer`/`AggregateRating` JSON-LD that *does* render for
  Googlebot is structurally valid.
- The city×category templated copy in `seoContent.js` is real, varying,
  non-boilerplate content — the problem is purely that it's invisible to
  crawlers today, not that it doesn't exist or is thin.
- No thin-content quality-gate violations — only 8 listings, nowhere near
  the 30-page warning threshold.
- A near-zero backlink profile is expected and not itself a finding for a
  days-old site — see `MARKETING.md` for the existing outreach plan.

## What I didn't get a clean automated read on

Several specialist passes (performance/CWV numbers, mobile-viewport visual
check, deep search-experience persona scoring) ran into tooling turn
limits during this session and didn't produce a finished score. Based on
direct knowledge of the codebase rather than tool output: images are
hotlinked from Unsplash with no optimization/lazy-loading, fonts load via
a render-blocking tag, and there's no code-splitting beyond Vite's
default — all real, fixable, but not independently *measured* this round.
Happy to re-run those specifically once the Critical items above land, or
you can request a Google PageSpeed Insights read directly via `/seo google
pagespeed <url>` if you'd rather get real field data.
